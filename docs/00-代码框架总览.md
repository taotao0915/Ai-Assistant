## 二、三层架构与依赖方向

```
┌──────────────────────────────────────────────────────────┐
│  UI 层        ChatScreen.kt                              │
│  · 只读 StateFlow（messages / isStreaming / ttftMs）      │
│  · 只做一件事：把用户输入交给 vm.send(text)                │
└───────────────────────┬──────────────────────────────────┘
                        │ 事件向上（send）／状态向下（collectAsState）
┌───────────────────────▼──────────────────────────────────┐
│  状态层       ChatViewModel.kt                            │
│  · 唯一的状态持有者（UI 层不许有业务状态）                  │
│  · 拼装历史消息（system + 多轮）→ 交给网络层                │
│  · 收到 delta → 追加到最后一条 → 触发 UI 重组               │
└───────────────────────┬──────────────────────────────────┘
                        │ suspend 调用（协程）
┌───────────────────────▼──────────────────────────────────┐
│  网络层       SseChatClient.kt                            │
│  · 序列化请求 → OkHttp POST → 判断流式/非流式               │
│  · 逐行读 SSE → 解析 delta → onDelta 回调                  │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS
┌───────────────────────▼──────────────────────────────────┐
│  云端    DashScope /chat/completions（qwen-plus）          │
└──────────────────────────────────────────────────────────┘
```

**铁律：依赖只向下。** ChatScreen 不认识 OkHttp，SseChatClient 不认识 Compose。
好处：W3 换 LangChain4j 时只动网络层，UI 一行不用改——这就是分层的价值。

## 三、一次请求的完整旅程（从点击到上屏，10 步）

```
① 用户输入文字，点发送按钮
② ChatScreen: vm.send(input) 并清空输入框
③ ChatViewModel.send()
   ├─ 校验：空输入 / 上一条还在生成 → 直接 return
   ├─ messages 追加两条：用户消息 + 空的 AI 占位消息（带 ▍光标）
   └─ isStreaming = true（发送按钮变灰，防连点）
④ 拼装 history：system 提示词 + 所有非空历史消息（user/assistant 交替）
⑤ viewModelScope.launch 启动协程 → SseChatClient.streamChat(history, …)
   └─ withContext(Dispatchers.IO) 切到 IO 线程（网络不能跑主线程）
⑥ SseChatClient：
   ├─ 校验 Key 非空
   ├─ ChatRequest 序列化成 JSON（encodeDefaults 保证 stream:true 在里面）
   ├─ OkHttp POST，带 Authorization + Accept: text/event-stream
   └─ execute() 拿到"响应头"（此时正文还在流式传输中）
⑦ 检查 Content-Type：
   ├─ 含 event-stream → 进入 SSE 循环（正常路径）
   └─ 是 application/json → 非流式兜底：整段读出，一次性上屏
⑧ SSE 循环：readUtf8Line() 逐行读
   ├─ 跳过非 data: 行
   ├─ 遇 [DONE] 结束
   └─ 每个 data 帧 → 解析出 delta.content → onDelta(delta)
⑨ 回调穿透回 ViewModel：
   ├─ onFirstToken → 记录 TTFT（首 token 延迟）
   └─ onDelta → 复制列表、追加到最后一条、赋值给 messages.value
⑩ Compose 检测到 messages 变化 → 只重组最后一条气泡 → 你看到"多打一个字"
最后：finally { isStreaming = false }（按钮恢复）；异常则把错误渲染成一条红色气泡
```

## 四、数据模型：5 个类分别在干什么

| 类 | 所在层 | 作用 | 关键字段 |
|---|---|---|---|
| `ChatMessage` | 协议 | 发给服务器的单条消息 | `role`（system/user/assistant）+ `content` |
| `ChatRequest` | 协议 | 请求体 | `model` / `messages` / **`stream`** / `temperature` |
| `StreamResponse` | 协议 | 流式响应的一帧 | `choices[0].delta.content` |
| `NonStreamResponse` | 协议 | 非流式完整响应（兜底用） | `choices[0].message.content`、`error` |
| `UiMessage` | 界面 | 屏幕上的一个气泡 | `isUser` / `content` / `isError` |

**为什么要区分 `UiMessage` 和 `ChatMessage`？**
`ChatMessage` 是"协议要求的样子"（必须 role+content）；`UiMessage` 是"界面需要的样子"
（要区分左右气泡、要能标红报错）。中间做一次映射，协议和 UI 各自演化互不干扰——
**这是面试可以讲的"防腐层"意识**。

**注意流式与非流式的字段差异**（高频面试点）：
- 流式：`choices[].delta.content`（增量片段，需要自己拼接）
- 非流式：`choices[].message.content`（完整回答，直接用）

## 五、三个"看起来奇怪但其实关键"的设计

1. **先插入一条空的 AI 占位消息**
   让气泡立刻出现（带 ▍），token 到了往里面追加。若等第一个 token 才建气泡，
   用户会有"发送后没反应"的错觉——UI 响应性的经典手法。

2. **`withContext(Dispatchers.IO)` + `readTimeout(0)`**
   前者：Android 主线程禁止网络操作，否则 `NetworkOnMainThreadException`。
   后者：流式连接可能持续几十秒，默认 10 秒超时会把流掐断。

3. **`encodeDefaults = true`（今晚踩的坑）**
   kotlinx.serialization 默认**省略等于默认值的字段**。`stream=true` 是默认值，
   不加这个配置，请求体里根本没有 `stream` 字段，服务器默默按非流式返回——
   表现就是"等 3-5 秒一次性出全文，没有打字机"。

## 六、日志地图（排障用）

统一标签 `SSE_CHAT`，对着日志就能定位每一层：

| 日志 | 位置 | 含义 |
|---|---|---|
| `App 启动` | MainActivity | 确认手机上跑的是最新构建 |
| `send() 被调用` | ViewModel | 点击事件到达状态层 |
| `输入为空/还在生成中` | ViewModel | 被前置校验拦下（不是 bug） |
| `请求发出: model=…` | 网络层 | 请求即将发出 |
| `响应到达: HTTP … Content-Type=…` | 网络层 | ★ 最关键：200≠正常，要看 Content-Type |
| `首个 token 到达` | 网络层 | TTFT 计时点 |
| `流正常结束, 共 x 字符` | 网络层 | 流式路径正常收尾 |
| `非流式响应(长度=…)` | 网络层 | 走了兜底路径（服务器没给流式） |
