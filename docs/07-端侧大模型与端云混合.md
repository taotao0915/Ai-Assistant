## 2. 为什么端侧？—— 先把动机想清楚

### 2.1 四条不可替代的价值

| 价值 | 说明 | 典型场景 |
|---|---|---|
| **隐私** | 数据根本不出设备 | 身份证、体检报告、私人笔记 |
| **离线** | 没网也能用 | 地铁、飞机、境外漫游 |
| **延迟** | 没有网络往返，也不受服务端排队影响 | 高频短问答 |
| **成本** | 高频轻任务不烧 token | 语音助手的日常寒暄 |

**⚠️ 面试高频陷阱**：如果你把"省钱"当成主要动机，面试官会立刻判定你没做过真东西 ——
因为端侧烧的是用户自己的电和算力，省下的钱是公司的。
**真正撑得起一个功能的是隐私和离线**：这两条是"云端根本做不到"，而不是"云端做得贵"。

### 2.2 端侧**做不到**什么（1B int4 的真实边界）

| 能力 | 端侧 1B | 说明 |
|---|---|---|
| 闲聊 / 简单事实问答 | ✅ | 主战场 |
| 文本改写 / 摘要 | ⚠️ 勉强 | 短文本可以 |
| Function Calling | ❌ | 遵循率极低，工具调用基本失效 |
| 知识库检索（RAG） | ❌ | KV Cache 塞不下几篇文档 |
| 长上下文（>1K） | ❌ | 开始胡言乱语 |
| 数学 / 代码 / 多步推理 | ❌ | 能力不足 |

记住这个边界，你就理解了为什么**必须有路由层**：
问题从来不是"用端还是用云"，而是"**这一句话交给谁**"。

## 3. 端侧内存账 —— 你的手机到底能跑多大？

这是端侧最硬的一课，也是最能体现工程能力的部分。

### 3.1 峰值内存三块

```
峰值 ≈ 权重 + KV Cache + 运行时缓冲
```

**第 1 块：权重**

```
理论值 = 参数量 × 量化位宽 / 8
实际值 ≈ 参数量 × 0.7 字节          （int4 经验系数）
```

为什么实际比理论大？两处"高精度例外"：

- `embedding` / `lm_head` 层通常保留 fp16（占参数量 10-15%，量化了反而伤效果）
- 量化是**分组**的（group=128），每组额外带 `scale` 和 `zero` 元数据

| 模型 | 理论 (int4) | 实际经验值 |
|---|---|---|
| 0.5B | 250 MB | ~350 MB |
| 1B | 500 MB | ~700 MB |
| 1.5B | 750 MB | ~1000 MB |

**第 2 块：KV Cache（真正的隐形大户）**

```
单 token 字节 = 2(K和V) × 层数 × kv_heads × head_dim × 2(fp16)
总占用       = 单 token 字节 × 上下文长度
```

以 Qwen2.5-1.5B（28 层、2 个 KV head、head_dim=128、2048 上下文）为例：

```
2 × 28 × 2 × 128 × 2 = 28,672 B ≈ 28 KB / token
28 KB × 2048        ≈ 57 MB
```

看起来不大 —— 但**它随上下文线性增长**。换成 7B（32 层、8 个 KV head）：

```
2 × 32 × 8 × 128 × 2 = 128 KB / token
128 KB × 2048        ≈ 256 MB
```

这就是为什么高端机也不敢随便开长上下文。KV Cache 是所有端侧方案的共同天花板。

> 顺带一个进阶知识点：**GQA（Grouped Query Attention）** 就是为这个发明的 ——
> 1.5B 的 `kv_heads=2` 而 `heads=12`，KV 头少 6 倍，KV Cache 直接省 6 倍。
> 面试问"为什么现在的模型都用 GQA"，答"省 KV Cache"就是满分。

**第 3 块：运行时缓冲**

算子临时张量、tokenizer、预处理。多模态（图片/音频）时更大。
经验值：留 **150-250 MB**。

### 3.2 安全系数 —— 端侧最容易被忽略的一条

```kotlin
availMemMb >= peakMemMb × 1.5
```

为什么要 ×1.5？因为模型加载后手机还要继续用（接电话、切 App、系统收内存）。
如果只按"刚好够"加载，系统的 **LMK（Low Memory Killer）** 会在后台把你干掉。

**这就是端侧最真实的约束：不是"能不能跑起来"，而是"能不能不被杀"。**

### 3.3 代码里的落地：`DeviceProfiler`

`DeviceProfiler.recommendTier()` 实现的就是上面这套判断，双条件：

```
总内存够  AND  当前可用内存够
```

只看总内存会翻车：8GB 手机看着够，但后台挂着 30 个 App 时可用只剩 1.2GB，加载即被杀。
另外还有两个**硬门槛**，不满足直接劝退：

| 条件 | 为什么 |
|---|---|
| `Build.SUPPORTED_64_BIT_ABIS` 非空 | 32 位进程地址空间只有 3-4GB，光模型就吃掉大半，必然 OOM |
| `isLowRamDevice == false` | 系统已标记为低内存设备，别硬上 |

档位映射表（`ModelTier`）：

| 档位 | 建议最低总内存 | 估算峰值 |
|---|---|---|
| 0.5B int4 | 4 GB | 550 MB |
| 1B int4 | 6 GB | 950 MB |
| 1.5B int4 | 8 GB | 1350 MB |

## 4. 量化 —— 凭什么能压到 1/4

### 4.1 基本原理

量化就是把 fp16 的权重映射到低比特整数：

```
w_int4 = round(w_fp16 / scale) + zero_point
w_fp16 ≈ (w_int4 - zero_point) × scale
```

- `scale`：缩放因子，决定"一个整数格代表多大幅度"
- `zero_point`：零点偏移，保证浮点的 0 能精确表示（对补零很重要）

**为什么必须分组（group-wise）？**
整层共用一个 scale，遇到"大部分权重都很小、个别特别大"的分布时，
小权重会被压成同一个整数 → 精度崩掉。
所以按 64/128 个权重一组，每组独立算 scale/zero。
**代价**就是前面说的那点额外元数据（这也是"实际比理论大"的原因之一）。

### 4.2 位宽怎么选（实践结论，直接背）

| 位宽 | 效果 | 结论 |
|---|---|---|
| **int4 (Q4)** | 精度损失几乎无感 | ✅ **端侧黄金标准** |
| int8 | 几乎无损，但体积翻倍 | 内存宽裕时可用 |
| Q2 / Q3 | 中文生成肉眼可见地糊 | ❌ 别碰 |

一个很好用的类比：int4 像 128kbps MP3（有压缩但基本听不出来），
Q2 像 32kbps（声音已经糊了）。

### 4.3 量化还能加速，不只是省内存

这是面试的加分点：**decode 阶段是访存密集（memory-bound）的** ——
每产 1 个 token 都要把全部权重从内存读一遍，算力根本用不满。
权重从 fp16 压到 int4，**要搬运的字节数变成 1/4**，
于是 decode 速度几乎直接提升数倍。所以量化是"省内存"和"提速"一举两得。

## 5. Prefill 与 Decode —— 必须分清的两个阶段

端侧优化的所有决策，都建立在这个区分上。

```
prompt（含 system + 历史 + 本轮） 
   │
   ├─【Prefill 预填充】所有输入 token 并行跑一遍，建立 KV Cache
   │     · 算力密集（compute-bound）→ GPU / NPU 的强项
   │     · 决定 TTFT（首字延迟）
   │     · 长 system prompt 时它是主要耗时
   │
   └─【Decode 解码】逐个生成 token，每产一个都要重跑一遍模型
         · 访存密集（memory-bound）→ 瓶颈在内存带宽，不在算力
         · 决定 TPOT（每 token 耗时）/ 吞吐 t/s
         · 这才是"打字机速度"
```

**结论（高频面试题）**：

> 优化 decode 靠**减少访存**：量化、算子融合、KV Cache 管理。
> 优化 prefill 靠**增加算力**：GPU/NPU 卸载、批处理。
> **方向完全不同，别搞混。**

### 5.1 指标口径（必须统一，否则端云没法比）

| 指标 | 定义 | 我们的代码 |
|---|---|---|
| **TTFT** | 从发请求到第一个 token 到达 | `GenStats.ttftMs`（= prefillMs） |
| **TPOT / 解码速度** | 平均每 token 耗时 | `GenStats.decodeCps`（字/秒） |
| **总耗时** | prefill + decode | `GenStats.totalMs` |

`MediaPipeLlmEngine.streamGenerate()` 里的口径和云端 TTFT **完全一致** ——
这样端云的延迟数字才能横向比较，否则"端侧 1.2 秒 vs 云端 0.8 秒"就是两个口径在比。

参考量级（1B int4、2048 上下文、骁龙 8 系）：

| 场景 | TTFT | 解码速度 |
|---|---|---|
| 短 prompt（<200 token） | 0.5-1.5 s | 15-30 字/秒 |
| 长 prompt（>800 token） | 2-5 s | 同上 |

注意 prefill 随 prompt 长度**近似线性增长**，而 decode 速度基本恒定。
这直接推出一个端侧 prompt 工程原则：**system prompt 越短越好**。

## 6. 引擎选型 —— 三个方案的真实成本

### 6.1 对比表（这些是逐个核实过的事实，不是印象）

| 引擎 | 分发形态 | 集成成本 | 模型格式 | 中文 |
|---|---|---|---|---|
| **MediaPipe** | Google Maven 的 AAR | ⭐ 一行 gradle | `.task`（专有） | 一般 |
| **llama.cpp** | 无官方 Android SDK | ⭐⭐⭐⭐ 自己写 JNI + CMake | GGUF（最全） | 好 |
| **MNN** | C++ 库 + 完整 App 工程 | ⭐⭐⭐ 编 so / 搬 app 层 | MNN 目录 | **好** |

### 6.2 MNN 的真实情况（重点，很多人搞错）

网上大量博客写 `implementation("com.alibaba:MNN-LLM:2.9.0")` —— **这个依赖不存在**。
去官方仓库核实后的事实：

- MNN **不在 Maven Central 发布 aar**
- GitHub Releases 只有 C++ 预编译包
  （`mnn_3.6.1_android_armv7_armv8_cpu_opencl_vulkan.zip`），不是 AAR
- 两条路：① 用 NDK 编译 `libMNN.so`（`project/android/build_64.sh`，需 NDK 27+）
  ② 下预编译 so 自己接
- **更麻烦的是 Java API 不是干净的库**：官方示例的 `LlmSession.kt` 直接
  `import` Gson / Timber / `ChatDataItem` / `ModelConfig` / `QnnModule` 等 app 内部类，
  想复用得把半个 demo 工程搬过来

**MNN 的优势也是真的**：对 Qwen 系列优化最好、中文效果最好、ModelScope 上
有现成转换好的模型（国内直连）。所以它是**生产环境的合理选择**，只是**起步成本高**。

### 6.3 我们的决策路径（这才是面试要讲的）

```
① 先用 MediaPipe 把"端云混合"的链路跑通     ← 集成成本最低，一天能出效果
② 用 OnDeviceLlm 接口把引擎隔离起来
③ 需要更强中文/更广模型支持时，再插一个 MnnLlmEngine 进来
```

面试时讲这段，比"我会用 MNN"有说服力得多 ——
因为它展示的是**成本意识 + 架构能力**，而不是"我照抄了个 demo"。

### 6.4 MediaPipe 的三个硬约束（踩之前先知道）

1. 只支持 Google 官方支持的模型（Gemma 系 + 少量 Llama 变体）。
   想跑 Qwen → 换 MNN / llama.cpp。
2. 官方已标记 **maintenance-only**，推荐迁移到 LiteRT-LM。
   但 API 稳定、文档齐全，仍是"最小成本验证"的最佳选择。
3. **不支持模拟器**，必须真机（NPU/GPU delegate 需要真实硬件）。

## 7. API 考古实录 —— W3 那套方法又救了一次

### 7.1 问题

官方文档（ai.google.dev）给的 Kotlin 示例是这样的：

```kotlin
val options = LlmInference.LlmInferenceOptions.builder()
    .setTopK(40)              // ← 猜的写法
    .setTemperature(0.8f)     // ← 猜的写法
    .setResultListener { ... }// ← 猜的写法
    .build()
```

照着写，**编译直接失败**。

### 7.2 方法论：不解压的 grep 是没用的

这是 W3 就吃过的亏：**jar/aar 里的 class 是 deflate 压缩的，
直接 `grep` 二进制搜字符串是假阴性**（第一次验证 1.5.0"干净"就是这么翻的车）。

正确姿势：

```bash
# 1. 下 aar（注意 tasks-genai 在 Google Maven，不在 Maven Central）
curl -sL -o mp.aar \
  https://maven.aliyun.com/repository/google/com/google/mediapipe/tasks-genai/0.10.27/tasks-genai-0.10.27.aar

# 2. 解包 → 取出 classes.jar → 再解包
unzip -o -q mp.aar -d aar
unzip -o -q aar/classes.jar -d cj

# 3. javap 逐类反编译，看真实签名
javap -classpath cj 'com.google.mediapipe.tasks.genai.llminference.LlmInference$LlmInferenceOptions$Builder'
```

### 7.3 实测结论（和文档不一致的三处）

```
LlmInference.LlmInferenceOptions.Builder 只有：
  setModelPath(String)  setMaxTokens(int)  setMaxNumImages(int)
  setMaxTopK(int)       ← 注意不是 setTopK
  setSupportedLoraRanks(List<Integer>)
  setVisionModelOptions(...)  setAudioModelOptions(...)
  setPreferredBackend(Backend)   ← Backend 只有 DEFAULT / CPU / GPU
  ⚠️ 没有 setTopK / setTemperature / setRandomSeed / setResultListener

采样参数其实在会话层：
LlmInferenceSession.LlmInferenceSessionOptions.Builder
  setTopK(int)  setTopP(float)  setTemperature(float)  setRandomSeed(int)
  setPromptTemplates(PromptTemplates)

流式靠这个（ProgressListener 是单方法接口 run(OutputT, boolean)）：
LlmInference.generateResponseAsync(String, ProgressListener<String>)
```

**三处不一致**：`setTopK`→`setMaxTopK`；采样参数不在 Options 层而在 Session 层；
流式不是 `setResultListener` 而是 `ProgressListener`。

**教训（写进简历的技巧点）**：
> 官方文档描述的是"某个版本"，你依赖的是"具体某个版本"。
> 端侧 SDK 迭代快、文档滞后是常态 —— **以你实际依赖的那份 aar 为准**。

### 7.4 顺便量出来的包体代价

```
aar/jni/arm64-v8a/libllm_inference_engine_jni.so   12.8 MB
aar/jni/armeabi-v7a/libllm_inference_engine_jni.so  8.3 MB
aar/jni/x86/libllm_inference_engine_jni.so         17.2 MB
aar/jni/x86_64/libllm_inference_engine_jni.so      14.7 MB
```

四个 ABI 全打进去 **+53MB**。所以 `defaultConfig.ndk.abiFilters` 裁到
`arm64-v8a + armeabi-v7a` 就够了（真机只有这两种）。

另外 aar 的 AndroidManifest 里声明了 `uses-native-library libOpenCL.so (required=false)` ——
这是 Android 12+ 的要求：用 vendor 提供的库必须显式声明。`required=false`
保证了没有 OpenCL 的机器也能装（自动降级 CPU）。

## 8. 端云路由 —— W7 架构的灵魂

### 8.1 决策树（`EngineRouter.decide()`）

```
输入：用户这一句 + 策略 + 端侧是否就绪 + 网络状态

① 策略 == 仅云端                → 云端
② 端侧未就绪                    → 云端（附原因，UI 可解释）
③ 无网络                        → 端侧  ←★ 离线兜底，最硬的价值
④ 命中「工具/检索/实时」意图      → 云端（端侧没有工具与知识库）
⑤ 命中「隐私」意图               → 端侧（数据不出设备）
⑥ 策略 == 优先端侧               → 端侧
⑦ 短问答（≤40 字）              → 端侧（省 token，延迟更低）
⑧ 默认                          → 云端（复杂任务给大模型）
```

### 8.2 两条设计原则（面试可讲）

**原则一：非对称代价 —— 阈值不该取中间值**

误判成端侧的代价（答错、答不了、用户失去信任）**远大于**
误判成云端的代价（多花几分钱 token）。

所以工具/检索词表宁可写宽一点，**多判给云端**。
这个"两边判错损失不一样时，阈值要偏向损失小的一侧"的思维，
是策略系统的通用设计原则。

**原则二：规则顺序即优先级**

为什么"工具意图"要排在"隐私意图"前面？

因为"我的备忘录"这句话同时命中"我的"（隐私）和"备忘录"（工具）。
如果先判隐私 → 走端侧 → 但端侧的 1B 模型**根本做不了备忘录检索** →
用户得到一个错误的答案，体验比"数据上云"差得多。

**所以：先判能力边界，再判偏好。**

### 8.3 端侧 Prompt 工程三条铁律

`HybridChatClient.buildDevicePrompt()`：

| 铁律 | 原因 |
|---|---|
| **短** | prefill 开销与长度线性相关；小模型的指令遵循能力还随长度急剧下降 |
| **结构化** | 用明确角色标记（`用户：` / `助手：`），别用自然语言描述格式 |
| **截断** | 历史限 2 轮 × 200 字。1B 模型的上下文极其宝贵 |

对照 W4 那份带完整工具清单的云端 system prompt，
端侧的只有一句：`"你是手机上的离线助手。回答简短、直接、用中文。不知道就说不知道。"`

### 8.4 手搓历史 vs 复用 Session（一个容易踩的坑）

MediaPipe 有两层对象，职责完全不同：

| 对象 | 持有 | 生命周期 |
|---|---|---|
| `LlmInference`（模型） | 权重 + 计算图 | **常驻**（加载要 3-8 秒） |
| `LlmInferenceSession`（会话） | KV Cache + 采样参数 | **每轮新建**（很轻） |

因为我们把"历史拼接"放在上层做了，会话必须是**无状态**的：
每轮新建 → 灌入完整 prompt → 生成 → 关闭。

**如果复用 session，它会自己累积上下文，和上层拼的历史重复，
小模型立刻开始胡言乱语。** 这是端侧多轮最容易踩的坑。

## 9. 三个必须做对的工程细节

### 9.1 native 内存不受 GC 管理

```kotlin
override fun onCleared() {
    hybrid.releaseDevice()      // ← 不写这一行，就是几百 MB 的泄漏
}
```

`LlmInference` / `LlmInferenceSession` 持有的是 native C++ 内存，
**JVM 的 GC 完全看不见它**。不显式 `close()`，即使 ViewModel 被回收，
那几百 MB 依然钉在进程里。

用户看到的现象是"手机越用越卡"、"其他 App 被系统杀掉"。
排查极难 —— 因为 Android Studio Profiler **默认只看 Java Heap**，
native 内存要切到 Memory Profiler 的 "Native" 视图才看得见。

### 9.2 线程模型（三层，一个都不能少）

| 阶段 | 线程 | 为什么 |
|---|---|---|
| 加载模型 | `Dispatchers.Default` | CPU 密集（建图、分配张量），不是 IO |
| 生成推理 | `Dispatchers.IO` | 同步阻塞，必须离开主线程（否则 ANR） |
| 更新 UI | 主线程 | Compose 状态更新 |

⚠️ **ProgressListener 的回调在 native 推理线程，不在主线程。**
直接在里面更新 UI 会崩 —— 这是端侧最经典的崩溃。

### 9.3 降级必须无缝

```kotlin
runCatching { deviceStream(...) }.getOrElse { 
    cloud.streamChat(...)      // 端侧失败 → 静默回退云端
}
```

**端侧是"增强"，不是"依赖"。** 这个定位决定了所有错误处理的方向：
用户没下模型、下了一半、手机 ABI 不对、加载 OOM —— App 都得照常能用。

### 9.4 模型文件分发（篇幅所限，只给结论）

**为什么不放 assets？** ① APK 破 1GB ② 安装解压耗时 ×10
③ 无法按机型差异化 ④ 换模型要发新版 APK。

**四种策略**：应用内下载（我们采用）/ Play Asset Delivery（国内不可用）/
随包分发（只适合 <100MB 的小模型，如端侧 embedding）/ 多 App 共享。

我们**不申请任何存储权限**：落在 `getExternalFilesDir()/ondevice/`，
属于应用私有沙箱，Scoped Storage 完全放行，`adb push` 也能直接写。

下载器用 `.part` 后缀 + **HTTP Range 断点续传**。
关键细节：**只有响应 206 才能 append，收到 200 必须从头写** ——
否则服务端不支持续传时文件会损坏。

## 10. 模型分发 —— 从"gated 踩坑"到可用的 App 内下载器

> 本节是 W7 的补充实现。最初的版本要求用户自己 `adb push` 模型文件进手机，
> 对开发者够用，对真实用户等于没做功能。补上"应用内下载"时，
> 撞上了一个**只有动手做过才知道的硬约束**。

### 10.1 硬约束：大部分官方端侧模型，App 内根本下不了

第一版方案写的是"从 MediaPipe 官方文档给的地址下载 `gemma3-1b-it-int4.task`"。
实际验证（`curl` 实测，不是猜）：

```
$ curl -sI https://huggingface.co/litert-community/Gemma3-1B-IT/resolve/main/...
HTTP/1.1 403 Forbidden
Access to model litert-community/Gemma3-1B-IT is restricted and you are not in
the authorized list.
```

这是 **gated（受限）模型**：服务端要求登录并明确接受许可协议才给下载。
Google 的 Gemma 全系列（1B/2B/4B/12B/27B）都是这个状态，Kaggle 上的也一样。

**为什么这对"App 内下载"是致命的**：

- 下载需要用户的账号 token，而**把 token 打进 APK 是安全事故** ——
  任何人反编译就能拿到，等于把你的账号公开给全世界；
- 让用户在 App 里登录 HF / 跳浏览器接受许可，转化率约等于 0；
- 所以这条路在"自动下载"这个需求下**直接是死的**，不是"体验差一点"。

> **结论（这条值得记一辈子）**：官方文档推荐的模型 ≠ 你能在 App 里自动下载的模型。
> 选型的第一个筛选条件不是"效果好不好"，而是"**文件拿不拿得到**"。
> 面试时讲"我调研过 Gemma 是 gated、所以换成 Qwen"，比讲"我用了 Gemma 1B"
> 高一个段位 —— 前者是工程判断，后者只是用过。

### 10.2 落地方案：换成非 gated 的 Qwen2.5

把 `litert-community` 组织下的模型全列出来，逐个查 `gated` 字段：

| 模型 | gated | 体积 | 中文 |
|---|---|---|---|
| Gemma3-1B-IT | `auto`（需授权）❌ | 557MB | 一般 |
| Gemma2-2B-IT | `auto` ❌ | 1.2GB | 一般 |
| **Qwen2.5-0.5B-Instruct** | **false** ✅ | 521MB | **好** |
| **Qwen2.5-1.5B-Instruct** | **false** ✅ | 1.49GB | **好** |

选 Qwen2.5 的三个理由：

1. **Apache 2.0 + `gated: false`** —— 谁都能直接下，不需要任何凭据；
2. README 明确写着 "ready for deployment on Android using the **MediaPipe LLM
   Inference API**" —— 与我们的 `tasks-genai` 引擎同源，文件格式就是我们能吃的 `.task`；
3. **中文能力远好于同尺寸的 Gemma / SmolLM**，这对中文助手是决定性的。

清单里放两个档位：0.5B（521MB，4GB 内存起，标"推荐"）和 1.5B（1.49GB，8GB 内存起）。
体积数字全部来自真实 URL 的 `Content-Length`，不是估的。

**文件名也是一份信息，别当乱码看**：

```
Qwen2.5-0.5B-Instruct_multi-prefill-seq_q8_ekv1280.task
     └── 模型      └── 多轮 prefill  └── 8bit └── KV Cache 1280 token
```

`ekv1280` 是**硬上限** —— prompt + 生成长度超过 1280 token 就会被截断，
所以引擎侧的 `maxTokens` 必须控在它之下。换模型时这个数要跟着看。

### 10.3 下载器必须处理的五件事

少一件用户就会来骂你 —— 这五条是"能不能上线"的分界线：

| # | 要处理的事 | 不做会怎样 | 实现要点 |
|---|---|---|---|
| ① | **断点续传** | 500MB 下到 80% 切后台就白下 | `Range: bytes=N-` 请求 + 判断 206 |
| ② | **完整性校验** | 半截文件被当成完整模型，加载时在 native 层崩 | 写入字节数 vs `Content-Length` |
| ③ | **多源回退** | 国内连不上官方域，功能直接废掉 | 镜像优先 + 失败逐个切换 |
| ④ | **磁盘预检** | 下到 90% 才发现空间不够 | 下载前算可用空间 vs 体积 + 预留 |
| ⑤ | **可取消** | 点错了只能杀进程 | `Job.cancel()` + **保留 .part** |

三个细节值得单独说：

**`.part` 后缀的价值**：下载中写 `xxx.task.part`，完成才 `rename` 成 `xxx.task`。
这样"下了一半"和"下完了"在**文件系统层面就是两种状态**，不需要额外记数据库。
而且同一文件系统内的 `rename` 是原子操作，不存在"改了一半"的中间态 ——
否则 App 被杀在改名中途，下次启动就会看到一个半截的正式文件，
还可能被当成"已就绪"送去加载，崩溃点离真正的原因十万八千里。

**换源时必须丢弃已有分片**：不同源的 ETag / 分片边界可能不同，把旧源的字节
和新源的字节拼在一起 = 文件损坏，**而且下载过程完全看不出来**（大小都对、
校验也过）。宁可多花流量重下，也不能产出损坏文件。

**进度上报必须节流**：每读一次 64KB 就推一次 StateFlow，Compose 每秒会重组
上百次，界面直接卡死。500ms 一次是人眼分辨率的甜点值 ——
进度条看起来是连续的，UI 线程又不会被淹。这类"高频事件节流"是通用模式。

### 10.4 一个静默的坑：prompt template

这段不写，端侧效果会莫名变差，而且**全程不报错**。

每个模型家族有自己的对话标记：

```
Qwen (ChatML)： <|im_start|>user\n ... <|im_end|>\n<|im_start|>assistant\n
Gemma：         <start_of_turn>user\n ... <end_of_turn>\n
```

MediaPipe 对 Gemma 系列内置了默认模板，但对 Qwen **不匹配**。拼错会怎样？
模型不报错，它会开始"续写对话文本"—— 把你的问题当成网页文本继续编下去，
一本正经地输出看起来像模像样的幻觉。

排查时你会怀疑量化、怀疑参数、怀疑内存，**都不会怀疑到格式上**。这就是它的危险之处。

代码里用 `PromptStyle` 枚举把六段标记（`userPrefix` / `userSuffix` / `modelPrefix`
/ `modelSuffix` / `systemPrefix` / `systemSuffix`）集中管理，通过
`LlmInferenceSessionOptions.setPromptTemplates()` 注入。换模型只换一个枚举值。

> 【面试可讲】这是"**静默失败**"的典型案例：不抛异常、不报错、只是结果变差。
> 端侧比云端更容易遇到 —— 云端服务端帮你把模板、分词、特殊 token 全藏起来了，
> 端侧全都暴露给你。**能想到查 prompt 格式，本身就是"做过端侧"的标志。**

### 10.5 别把"下载"和"加载"合成一个按钮

一个容易做错的产品决策：下载完自动加载模型。

不该这样。因为：

- 下载是**网络 + 磁盘**操作，用户可能想"先下好、晚点再用"；
- 加载要吃掉 800MB~1.9GB **内存**，必须由用户明确触发 ——
  否则用户一进设置页就莫名卡顿，甚至被系统 LMK 杀后台。

所以下载完成后只做两件事：刷新端侧可用状态 + 给一句人话提示
（"点「加载模型」即可启用"）。**状态是机器的，动作是人的** ——
这条边界在端侧产品里尤其重要，因为端侧的资源代价是真金白银。

## 附录：真机首跑崩溃记录 —— Kotlin 构造期 NPE

W7 代码写完、编译通过、打包通过，**装到真机启动瞬间就崩了**。
这个坑不属于"端侧"，属于 Kotlin 语言本身，但它是 Android 工程里最高频的
"拷问式"崩溃之一，值得完整记一遍。

### 崩溃堆栈（关键三行）

```
java.lang.RuntimeException: Cannot create an instance of class com.workbuddy.assistant.ui.ChatViewModel
Caused by: java.lang.NullPointerException: Attempt to invoke virtual method
           'int kotlin.collections.ArrayDeque.size()' on a null object reference
    at HybridChatClient.buildInitialStatus(HybridChatClient.kt:150)
    at HybridChatClient.<init>(HybridChatClient.kt:87)          ← 注意是构造函数！
    at ChatViewModel.<init>(ChatViewModel.kt:74)
```

### 怎么读这个堆栈（这是通用的排障路径）

**第 1 步：先别被最外层骗了。**
`Cannot create an instance of class XxxViewModel` 只是个**结果**——ViewModel 工厂
（`AndroidViewModelFactory`）反射调构造函数，构造函数抛了异常，它就把异常包一层抛出来。
真正的信息在 `Caused by:` 里。**永远往下看到最深的 `Caused by`。**

**第 2 步：看 NPE 读的是什么类型的字段。**
`kotlin.collections.ArrayDeque.size()` —— 注意 `kotlin.collections` 前缀：
这是**我们自己代码里的 Kotlin 容器**，不是框架内部的。`
这说明崩溃点在我们的类里，怀疑范围立刻从"MediaPipe 是不是不兼容"缩小到"我们哪写错了"。

**第 3 步：注意到第二帧是 `<init>`。**
`HybridChatClient.<init>(HybridChatClient.kt:87)` —— 也就是说，
**这次崩溃发生在"对象还没构造完"的阶段**。这一步基本就锁定了病种：构造期字段初始化问题。

**第 4 步：回去看第 87 行和第 150 行在干什么。**

### 根因

```kotlin
class HybridChatClient(...) : ChatClient {

    private val _deviceStatus = MutableStateFlow(buildInitialStatus())  // 第 87 行 ← 初始化时就要执行方法
    ...
    private val deviceHistory = ArrayDeque<Pair<String, String>>()      // 第 99 行 ← 但它在这里才赋值

    private fun buildInitialStatus(): DeviceStatus {
        ...
        val historyCount = deviceHistory.size    // 第 150 行 ← 读到 null
    }
}
```

**Kotlin 的成员字段是在构造函数里按声明顺序逐个赋值的**（等价于 Java 里从下往上排的一串
`this.x = ...`，只是顺序按你的书写位置）。所以执行到第 87 行时，`deviceHistory` 还是
引用类型的默认值 `null`，读 `.size` 立刻 NPE。

> 有 Java 经验的人容易在这里踩坑：Java 里字段初始化是"先全部置默认值（null/0），
> 再按顺序执行初始化器"，Kotlin 完全一样。区别在于 Kotlin 让你写得更像声明，
> 看起来"不存在顺序问题"，于是更容易忘。

### 为什么编译期不报错（这点最值得记）

Kotlin **只禁止局部变量的前向引用**，对**成员字段**的前向引用是完全合法的：

```kotlin
fun f() {
    println(x)      // ❌ 编译错误：Variable 'x' must be initialized
    val x = 1
}
```

```kotlin
class A {
    fun f() = x      // ✅ 编译通过，运行时才可能拿到 null
    val x = 1
    val y = f()      // ⚠️ y 初始化时 x 还没赋值 —— 编译器不管
}
```

编译器在这里选择"信任你"，因为成员方法可能在对象构造完之后才被调用（那是完全合法的）。
它无法静态判断你是不是在构造期就调了它。**所以唯一的防线是纪律。**

### 修复

把 `deviceHistory` 的声明**上移到 `_deviceStatus` 之前**：

```kotlin
    private val prefs = context.getSharedPreferences("on_device", Context.MODE_PRIVATE)

    /** 端侧对话历史（手搓的最小滑动窗口，最多 2 轮） */
    private val deviceHistory = ArrayDeque<Pair<String, String>>()   // ← 必须在这

    private val _policy = MutableStateFlow(...)
    private val _deviceStatus = MutableStateFlow(buildInitialStatus())  // ← 这里会读它
```

代码里我在两处都留了注释（字段声明处 + `buildInitialStatus()` 处），
因为这是**那种"后人重构时随手一挪就再次引爆"的坑**，注释比记忆可靠。

### 记住这三条规则

1. **构造期代码（属性初始化、`init {}` 块）读到的字段，必须声明在它之前。**
2. **构造期方法只做无副作用的纯计算。** 别在里面发起网络、读文件、加载模型 ——
   那些都该等 UI 触发（`buildInitialStatus()` 现在只读 `repository`/`profile`/`deviceHistory`
   这三个已经声明在前面的字段，其他字段此刻全是 null）。
3. **同类变体要知道**：
   - 构造期调用 `open`/可被子类覆盖的方法 → 子类字段还没初始化，拿到 null
   - `object` 里的属性互相引用（`object` 是首次访问时按序初始化，同样会踩）
   - ViewModel 构造签名不匹配 → 也是 `Cannot create an instance of class`，
     但 `Caused by` 是 `NoSuchMethodException` 而不是 NPE —— **同样一行报错，两种完全不同的病**，
     必须靠 `Caused by` 区分（W4 加 `AndroidViewModel(application)` 时我们踩过这个）

### 排查清单（下次直接照做）

```
① 看最内层 Caused by，忽略最外层那句 "Cannot create an instance of..."
② 若是 NoSuchMethodException → 查 ViewModel 构造签名 vs 工厂参数
③ 若是 NPE 且第二帧是 <init> → 构造期问题，回去查字段声明顺序
④ 找到"被读的字段"，看它是否声明在读取点之后 → 上移即可
⑤ 顺手检查同一个类里其它"构造期方法"，别只修一处
```

## 附录二：设置面板滑不动 —— Compose Modifier 顺序坑（无日志可查）

修完崩溃之后，模型能下载了，但设置面板里**模型列表滑不动**，
超出屏幕部分被裁掉。这次的麻烦是：**一行异常日志都没有。**

这正是 Compose 布局问题的特点 —— **约束链算错的后果是"画面不对"，不是崩溃**。
没有堆栈可看，只能推约束。

### 根因：Modifier 顺序写反

```kotlin
// ❌ 原代码
Modifier
    .verticalScroll(rememberScrollState())   // 在外层
    .heightIn(max = 430.dp)                  // 在内层
```

### 推导一遍（推完就永久记住）

先说清楚 Compose 的规则：

> **Modifier 链从左到右 = 从外层到内层。测量时外层先执行，再把约束传给内层。**

于是上面这段的执行过程是：

| 步骤 | 发生了什么 |
|---|---|
| ① | `verticalScroll` 先测量子节点，并给它**无限高**约束（"你随便长，滚动我来负责"） |
| ② | 子节点 `heightIn(max = 430.dp)` 收到无限高约束 → 把自己的高度**封顶 430dp** |
| ③ | Column 里内容实际有 900dp，被压成 430dp 报上去 |
| ④ | `verticalScroll` 拿到子高度 430，视口也是 430 → **可滚动范围 = 0** |

**滚动范围 = 子内容高度 − 视口高度。** 这里两项相等，于是死锁：
滑不动，而且超出部分也没有任何容器负责显示。

### 修复

```kotlin
// ✅ 正确：让 heightIn 在外层限死视口，verticalScroll 在内层把内容放开
Modifier
    .heightIn(max = maxContentHeight)
    .verticalScroll(rememberScrollState())
```

顺序一换，第 ④ 步就变成：视口 430、内容 900 → 可滚动范围 470 → 正常。

同时加了一句自适应，因为**固定 430dp 在小屏、横屏、大字体下依然会溢出**：

```kotlin
val screenHeight = LocalConfiguration.current.screenHeightDp.dp
val maxContentHeight = (screenHeight * 0.6f).coerceAtMost(430.dp)
```

### 记住这条铁律

> **凡是"限制尺寸"和"允许滚动"要同时用的地方，限制尺寸的必须写在滚动的前面。**

同类场景（一样容易写反）：`Modifier.height(200.dp).horizontalScroll(state)`、
`Modifier.size(...).verticalScroll(...)`。

### 为什么编译期抓不到

布局是**运行时按约束计算**的，修饰符顺序不影响任何类型检查。
编译器看到的是一个合法的 `Modifier` 链，它没有任何理由报错。
这类问题唯一的防线是：**改完跑一遍真实滑动，而不是只看编译通过**。

### 顺带记住两个相关坑

1. **Material3 的 `AlertDialog` 不会帮你滚动 `text` 槽内容。**
   内容超长它只会溢出屏幕，必须自己加 `verticalScroll`。
2. **禁止同向嵌套滚动。** 外层 `Column(verticalScroll)` 里再放一个
   `LazyColumn`（无固定高度）会直接抛
   `IllegalStateException: Vertically scrollable component was measured with an
   infinity maximum height constraint`。要么给内层固定高度，要么外层别滚。
   我们现在模型只有 2 个，用 `forEach` 平铺在同一个滚动容器里 —— 模型数量涨到十几个时
   需要重构成"外层不滚 + 内层 LazyColumn"。
