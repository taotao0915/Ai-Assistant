# 06 — RAG 进阶与评估优化：从"能跑"到"可度量"

> 前置：05（RAG 与端云混合）。W6 目标：把 W5 的"最小可用 RAG"
> 升级成"可优化的 RAG"，并且**用数字说话**。

## 1. W5 版本有哪三个软肋

| 软肋 | W5 做法 | 后果 |
|---|---|---|
| 切块 | 固定 300 字硬切 | 句子被腰斩，语义碎片化 |
| 检索 | 单阶段向量 TopK | "字面像但答非所问"的块排前面 |
| 评估 | 靠肉眼看回答 | 改一版参数不知道是变好还是变坏 |

W6 逐一解决 —— 而这个"发现问题 → 改造 → 度量"的循环，正是课程 26 讲
「评估优化」的核心方法论。

## 2. 升级一：语义切块（`semantic_chunk`）

两级策略：

1. **段落优先**：空行是作者亲手画的语义边界，先按段落切
2. **超长段落再按句子合并**：以 `。！？；` 切句，贪心拼到接近 `max_size`
3. **重叠 overlap**：相邻块共享尾部若干字，防止"答案正好被切在边界"

对比 05 的固定长度硬切：同样是 400 字上限，语义切块的每一块都**落在
自然边界上**，检索时命中的块读起来更完整，模型也更容易用。

## 3. 升级二：两阶段检索（W6 最重要的原理）

```
用户问题
   │
   ├─ ① 向量粗排（双编码器）: query 和 doc 各自独立编码 → 快
   │      召回 coarse_k=20 个候选（宁可多捞，别漏）
   │
   └─ ② Rerank 精排（交叉编码器）: query 和 doc 拼在一起喂模型打分 → 准
          选出 final_k=4 个，塞进上下文
```

**为什么两种编码器差别这么大？**

- **双编码器（向量检索）**：query 和文档从未"见面"，各自编码成向量后比距离。
  快（可预计算、可索引百万级），但表达力有限 —— 它衡量的是"语义相似"，
  不是"这段文字能否回答问题"。
- **交叉编码器（Rerank）**：把 `query + 文档` 拼成一条输入让模型通读打分，
  能捕捉细粒度的问答关系。准，但每个候选都要跑一次前向，慢 —— 所以只对
  粗排的 20 个候选做，不做全库。

这就是工业界标准架构：**召回用向量，排序用 Rerank**。
代码在 `rag_core.retrieve()`，两行就能看懂，但它是 RAG 提效性价比最高的一刀。

**降级设计**：没有 API Key 时 `rerank()` 直接返回粗排结果而不是抛错 ——
生产系统的容错习惯：**可选增强项失败，不能让主流程挂掉**。

## 4. 升级三：评估指标（没有度量就没有优化）

`eval.py` 输出三个数字，口径必须说清（面试会追问）：

| 指标 | 定义 | 衡量什么 |
|---|---|---|
| **HitRate@K** | TopK 里只要有正确块，这次就算命中 | 有没有找到 |
| **Recall@K** | 正确块被召回的比例 | 找全了没有 |
| **MRR** | 第一个正确结果排名倒数的均值 | 排得好不好（越靠前越高，上限 1.0） |

`--compare` 跑四组配置给你一张对比表，读法就写进脚本输出里了。
**注意**：MRR 对 Rerank 特别敏感 —— 如果 Rerank 生效，MRR 应该明显上升
（正确块从第 5 位挪到第 1 位，MRR 从 0.2 变 1.0）。

## 5. 工程化设计：为什么把代码拆成三个文件

```
backend/
├── main.py      路由层：只管 HTTP（参数校验 + 返回）
├── rag_core.py  核心层：Embedder / 切块 / 检索 / Rerank / 指标
├── eval.py      评估脚本：命令行跑对比实验
└── tests/smoke_test.py   离线冒烟测试（无需 API Key）
```

两个关键抽象：

**① `Embedder` 可插拔**（`DashScopeEmbedder` / `LocalHashEmbedder`）
把"文本→向量"抽成接口，换来的是：**没有 Key、断网也能跑通整条流水线**，
单元测试不再依赖外部 API。生产上还能无痛换模型（比如换成本地 bge 模型）。

**② 向量库存 `embedder` 元信息**
换 embedding 模型必须重建库 —— 否则向量空间不一致，检索全是噪声。
`VectorStore.search()` 会在维度不匹配时**直接报错**，而不是默默返回错结果。
这是生产事故的常见根因，我们用几行代码把它变成"不可能发生"。

2. **构造失败样本**：故意问一个知识库里没有的问题，看 `HitRate` 不变但回答

   观察指标暴跌 —— 亲手确认"embedding 质量决定检索上限"
4. **思考**：如果知识库有 100 万块，`VectorStore` 里那行 numpy 还能用吗？
   （答：不能，全量扫描是 O(N)。这时才需要 FAISS/Milvus 的近似最近邻索引 ——
   你知道原理之后再上向量库，才不会变成"调包侠"）
