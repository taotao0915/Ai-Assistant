## 0. 先纠正一个把很多人带偏的说法

我上一轮把 L1 那套（App 调 PC 后端检索）叫作「手机上的 RAG」，这个说法是**错的**，
你会看不懂，很大程度是被这句话误导。

先把定义掰开：

**RAG = Retrieval-Augmented Generation = 检索增强生成。**

它描述的是一个**模式**：

```
先找资料  →  把资料塞进 prompt  →  让模型基于资料回答
```

注意：这个定义里**完全没有提到"在哪台机器上检索"**。

所以"手机调 PC 后端检索"这件事，**是 RAG**，只是它的检索执行位置不在手机上。
按位置分，RAG 有三种拓扑：

| 拓扑 | 检索在哪 | 生成在哪 | 断网可用？ | 典型场景 |
|---|---|---|---|---|
| **L0 纯云端** | 云 | 云 | ❌ | 企业知识库问答、客服机器人 |
| **L1 客户端-服务端** | 你的服务器/PC | 云 | ❌ | 我们之前那套 |
| **L2 全端侧** | 手机 | 手机 | ✅ | Apple Intelligence、笔记 App 本地搜索 |

你问"这不叫 RAG 吧"——**它叫 RAG，但不叫端侧 RAG**。
你问"不是离线也能用吗"——**端侧 LLM 能离线，但检索不能**。这是两个独立的能力。

## 1. 为什么断网就查不了资料：缺的不是一件，是两件

端侧 RAG 需要**三件套同时存在**：

| 件 | 作用 | W7 时的状态 |
|---|---|---|
| ① 本地 embedder | 把文字变成向量 | ❌ 没有 |
| ② 本地向量索引 | 存向量 + 算相似度 | ❌ 没有 |
| ③ 本地 LLM | 拿片段写答案 | ✅ MediaPipe |

当时只有 ③。所以断网时：

```
你问"我的学习计划是什么"
  → 需要先把问题变成向量，去和资料比对     ← 这一步要调 PC 后端
  → 断网 → 整条链路断在这里
  → 模型再强也没用，因为它拿不到资料
```

**这就是"端侧 LLM 已就绪，但离线问资料仍然失败"的完整因果链。**

一句话记住：**LLM 是"会写字的人"，检索是"会找书的人"。有写字的人，没有找书的人，你问他书里写了什么，他只能编。**

## 2. 端侧 embedding 到底能不能做？我核实到的事实

不是查文档抄的，是把 aar 拉下来 `javap` 反编译确认的（W3 那套方法）。

### 2.1 API 是存在的，而且很干净

```java
// com.google.mediapipe.tasks.text.textembedder.TextEmbedder
public static TextEmbedder createFromFile(Context, File) throws IOException;
public TextEmbedderResult embed(String text);
public static double cosineSimilarity(Embedding a, Embedding b);   // 官方连余弦都给了
```

`cosineSimilarity` 是静态方法，这说明"端侧算相似度"是官方支持的正当用法，
不是我们硬凑的黑科技。

配置项只有三个：

```java
TextEmbedderOptions.builder()
    .setBaseOptions(BaseOptions.builder().setModelAssetPath(path).build())
    .setL2Normalize(true)    // 归一化 → 余弦退化成点积
    .setQuantize(false)      // 不量化，保精度
    .build();
```

### 2.2 但官方只有一个"英文"模型

我逐个探测了 Google 托管的地址：

| 模型 | 结果 | 体积 |
|---|---|---|
| `universal_sentence_encoder.tflite` | ✅ 200 | 6,120,274 字节 |
| `universal_sentence_encoder_multilingual.tflite` | ❌ 404（试了三个路径全 404） | — |
| `average_word_embedder.tflite` | ✅ 200 | 774,339 字节 |

**官方没有多语言版本。** USE 是用英文语料训练的。

### 2.3 一个致命的工程约束：只有 arm64

解包 `tasks-text-0.10.26.aar`，`jni/` 目录里只有一个文件：

```
jni/arm64-v8a/libmediapipe_tasks_text_jni.so   7.3MB
```

**没有 armeabi-v7a，也没有 x86_64。**

后果：
- 32 位 arm 手机 → 用不了；
- **模拟器 → 也用不了**（模拟器是 x86_64）。

而且不预检查的话，`createFromOptions` 会抛 `UnsatisfiedLinkError` ——
它是 `Error` 不是 `Exception`，`catch (Exception)` 抓不住，App 直接崩。

所以代码里第一件事就是查 ABI：

```kotlin
if (!Build.SUPPORTED_ABIS.contains("arm64-v8a")) {
    return RetrieverState.Failed("当前 ABI 不支持，向量检索仅 arm64-v8a")
}
```

> **本质**：端侧功能的可用性不是"代码写对就行"，它被**设备矩阵**卡着。
> 产品上必须接受"部分机型只能降级"，而不是假装所有人都一样。

## 3. 中文怎么办：双路召回（本节是重点）

### 3.1 表层现象

拿英文模型编码中文，会发生什么？

```
query: "怎么提升记忆效率"
资料A: "组块化可以把 7±2 个信息单元压缩成一个"   ← 语义高度相关
资料B: "周末去超市买牛奶和鸡蛋"                  ← 完全不相关
```

理想情况 A 的余弦远高于 B。但 USE 的中文语义空间是"顺带学到的"，
实际跑出来两个分数可能都在 0.2~0.3 之间抖动 —— **排序基本随机**。

### 3.2 机制层：为什么会这样

embedding 模型的本质是**把文本映射到一个高维空间，让语义相近的点距离近**。

这个空间的"坐标系"是**训练语料决定的**：
- 英文语料里，"chunking" 和 "memory" 经常在邻近上下文出现 → 两个向量被拉近；
- 中文语料在 USE 的训练集里占比极低 → "组块化"和"记忆"在这个空间里**没有被建立关系**。

所以不是"中文效果差一点"，而是**这段空间对中文几乎是空的**。
你往里投影中文，得到的坐标没有语义意义。

### 3.3 本质层：检索不一定要靠向量

这里的思维转折很重要：

> **"语义检索"是 RAG 的一种实现，不是 RAG 的定义。**

RAG 的定义只要求"找到相关资料"。找资料的方法有三种：

| 方法 | 原理 | 中文友好度 | 端侧成本 |
|---|---|---|---|
| 稠密向量（embedding） | 语义空间距离 | 依赖模型 | 需 6MB 模型 |
| 稀疏字面（BM25 / n-gram） | 词/字面重合 | ✅ 天然友好 | **零依赖** |
| 混合（hybrid） | 两路召回 + 融合 | ✅✅ | 低 |

**结论：端侧做中文检索，字面那一路才是主力，向量是补充。**

### 3.4 中文为什么用 bigram 而不是分词

中文没有空格。要做词级检索必须先分词，而端侧分词两条路都不划算：

- **带词典**（jieba 移植）：词典本身几 MB，还要处理未登录词；
- **跑模型**：为了检索再加载一个模型，内存和延迟都不值。

bigram（相邻两字）是"零依赖的近似分词"：

```
"学习计划" → {学习, 习计, 计划}
"端侧RAG"  → {端侧, 侧r, ra, ag}   ← 新词也能命中，不需要词典收录
```

它不是土办法：**很多搜索引擎对中文的默认处理之一就是 n-gram**，
因为它天然覆盖未登录词，代价只是召回略高。这是经过权衡的工程选择。

代价怎么补？用余弦形式的分母压一下：

```
score = |A ∩ B| / sqrt(|A| × |B|)
```

为什么不用 Jaccard（`|A∩B| / |A∪B|`）？因为 300 字的资料 vs 10 字的 query，
Jaccard 的分母会被长文本稀释到接近 0，**无论多相关都排不上来**。
几何平均分母对长度差异更宽容。

## 4. 两路怎么合？RRF，不是加权求和

### 4.1 一个几乎所有人第一次都会写错的地方

```kotlin
// ❌ 错
val score = 0.7 * vectorScore + 0.3 * lexicalScore
```

为什么错？因为两个分数的**量纲和分布完全不同**：

- 余弦相似度范围 `[-1, 1]`，中文场景实际集中在 `0.15~0.45`；
- bigram 余弦范围 `[0, 1]`，命中时能到 `0.4~0.7`。

把它们加权相加，等于假设"0.3 分代表的含义相同"。这是**把身高和体重相加**。

结果：某一路的分数天然更大，另一路被淹没。你会以为"向量没用"，
其实是权重被分布差异吃掉了。

### 4.2 RRF：只看排名，不看分数

```
score(d) = Σ_i  w_i / (k + rank_i(d))
```

- `rank_i(d)`：文档 d 在第 i 路里的排名（0, 1, 2...）
- `k`：平滑常数，通常 60（文献默认值）
- `w_i`：这一路的权重

**为什么它免疫量纲差异**：它只用"第几名"，不用"多少分"。
第 1 名恒等于 `1/(60+0)`，不管那一路的原始分是 0.9 还是 0.09。

代码里：

```kotlin
byVector.forEachIndexed { rank, i ->
    if (cells[i].vec >= VEC_MIN) fused[i] = (fused[i] ?: 0.0) + W_VECTOR / (RRF_K + rank)
}
byLexical.forEachIndexed { rank, i ->
    if (cells[i].lex >= LEX_MIN) fused[i] = (fused[i] ?: 0.0) + W_LEXICAL / (RRF_K + rank)
}
```

中文场景 `W_LEXICAL = 1.2 > W_VECTOR = 1.0` —— 因为字面那一路更可靠。
**这个倾斜是刻意的，也是必须在注释里写清楚的**，否则后人会以为是拍脑袋。

### 4.3 阈值为什么重要

如果只做融合不设阈值，`fused` 里会包含大量"两路都很低"的块 ——
RRF 只看排名，**排名永远存在**，哪怕所有分数都是噪声。

所以要先过滤：

```kotlin
VEC_MIN = 0.30    // 余弦下限
LEX_MIN = 0.08    // bigram 余弦下限
```

没命中就返回空列表，让上层说"知识库里没有相关内容"——**这比硬答强一百倍**。

> 这四个数（两个阈值 + 两个权重）是**经验值，必须靠评估集调**。
> 这也是 W6 做 eval.py 的价值：没有评估集，调参就是玄学。

## 5. 切块：为什么是 320 字 + 60 字重叠

### 5.1 上限由 KV Cache 倒推

Qwen2.5 的 `.task` 文件名里写着 `ekv1280` —— KV Cache 容量 1280 token。
**这个容量同时包含 prompt 和生成的内容**。

中文约 1.5 字/token，倒推预算：

```
资料 600 字   ≈ 400 token
历史 1 轮     ≈ 130 token
问题          ≈  50 token
─────────────────────────
prompt 合计   ≈ 580 token
留给生成      ≈ 700 token   （maxTokens 512，够）
```

所以 `MAX_CONTEXT_CHARS = 600`，单块 `MAX_CHUNK = 320`。

**贪心塞满 2000 字的结果**：模型刚"读完"资料就被截断，
或者根本没有预算生成 —— 表现为"回答到一半突然停住"。
这不是模型笨，是预算算错了。

### 5.2 为什么必须重叠

```
块1: ...第一阶段的重点是 Python 基础，第二阶段的重点
块2: 是机器学习，第三阶段...
```

"第二阶段的重点是机器学习"这句话被切成两半：
- 块1 里它不完整 → 向量特征不完整；
- 块2 里它没头没尾 → 同样不完整。

检索时两头落空。重叠 60 字（约一句话）保证**任何一句话至少完整出现在一个块里**。

代价：索引体积 +20%，且同一文档容易多块命中。
后者用 `MAX_CHUNKS_PER_DOC = 2` 收口 —— 否则喂给模型的 3 段全是同一段话的复制品。

## 6. 存储格式：为什么向量存 Base64 不存 JSON 数组

### 6.1 表层：体积差 3 倍

一个 float 用 JSON 文本表示：

```
0.123456789,     ← 12 字节
```

存成 4 字节小端二进制：**4 字节**。

512 维 × 1000 块：
- JSON 数组 ≈ 6MB
- Base64 ≈ 700KB（Base64 自身膨胀 4/3，但基数小得多）

### 6.2 机制层：解析成本才是大头

`Json.decodeFromString` 要解析 **50 万个浮点数字符串** ——
逐字符扫描、类型判断、字符串转 double，在手机上要好几秒。

Base64 解码是 `memcpy` 级别的操作，几十毫秒。

**这就是"冷启动时用户以为 App 卡死"的典型来源**：不是逻辑慢，是格式选错。

### 6.3 代码

```kotlin
private fun encodeVector(v: FloatArray?): String {
    val buf = ByteBuffer.allocate(v.size * 4).order(ByteOrder.LITTLE_ENDIAN)
    for (f in v) buf.putFloat(f)
    return Base64.encodeToString(buf.array(), Base64.NO_WRAP)
}
```

**必须指定字节序**（`LITTLE_ENDIAN`）。不指定就用平台默认，
换架构（arm → x86）时读出来的浮点数是乱的 —— 而且是那种"不崩溃、只是结果全错"的乱。

## 7. 路由上的一个真矛盾（这节面试很能讲）

### 7.1 矛盾是什么

`EngineRouter` 的规则里有：

```
④ 命中工具/检索词 → CLOUD    （1B 模型调工具能力基本为零）
```

"我的笔记""资料""计划"这些词会命中 ④，被判给**云端**。

但端侧知识库建好之后：**云端访问不到手机里的索引**。
判给云端 = 必然答不出来。

### 7.2 解法：把顺序反过来

```kotlin
// 先问本地知识库"你认识这个问题吗"
val hits = if (engineReady) retriever.search(userText) else emptyList()

val decision = if (hits.isNotEmpty()) {
    RouteDecision(RouteTarget.DEVICE, "命中本地知识库 ${hits.size} 段，走端侧生成")
} else {
    router.decide(...)   // 不认识，才回到原来的规则
}
```

关键洞察：**"检索"和"生成"是可以拆开的两个任务。**

- 检索：交给确定性的算法（余弦 + bigram），**1B 模型完全不参与**；
- 生成：拿 3 段现成资料写答案 —— 这个任务 0.5B 能胜任。

原来那条规则担心的是"小模型做不了复杂检索"，但经过我们自己的检索器之后，
**小模型根本不需要会检索**。规则的前提变了，结论就该变。

### 7.3 代价（必须承认）

端侧引擎未就绪时，知识库问题只能走云端，而云端没有索引 → 答不上。

这是 L2 全端侧架构的**固有边界**，不是 bug。
L1 混合架构没有这个问题（但 L1 断网就废）。**没有两全的架构，只有明确的取舍。**

## 8. prompt 怎么拼（端侧 RAG 的最后一公里）

```kotlin
if (hits.isNotEmpty()) {
    sb.append("请只依据下面资料回答。资料里没有的信息，直接说「资料里没有提到」。\n\n")
    sb.append(retriever.buildContext(hits))   // 【资料1·标题】...
    sb.append("\n\n")
}
```

四条要点：

1. **资料带标题和编号**：小模型分不清段落边界，编号能让它引用时对得上；
2. **必须给"不知道"的出口**：不给出口，检索没命中时它**一定会编**。
   这是 RAG 系统最常见的失败模式；
3. **有资料时历史只带 1 轮**：KV Cache 1280 token，资料已吃掉大半；
4. **资料在前、问题在后**：小模型对"最后出现的内容"注意力最强。
   这是长上下文里 "lost in the middle" 现象的朴素应用。

## 9. 怎么用（真机操作）

### 9.1 前置条件

- **64 位 arm 真机**（`arm64-v8a`）。模拟器不行 —— `tasks-text` 没有 x86_64 的 so。
- 端侧对话模型（Qwen2.5-0.5B，521MB）建议先装好；没有它，导入能成功但**回答会走云端**（云端没有你的索引）。

### 9.2 五步

```
① 装 APK → 右上角设置
② 「端侧知识库」→ 下载向量模型（6MB，几秒）
③ 点「启用语义检索」→ 显示"512 维"
④ 「＋ 导入笔记」→ 填标题 + 粘贴正文 → 导入
⑤ 回到对话，直接问：
     "我的学习计划第二阶段是什么"
     "笔记里关于记忆的部分说了什么"
```

### 9.3 验证它真的走了端侧

```bash
adb logcat -s ON_DEVICE_RAG ON_DEVICE
```

应该看到：

```
检索完成: "我的学习计划第二阶段是什么" → 3 块 / 42ms（向量+字面）
路由决策 → DEVICE（命中本地知识库 3 段，走端侧生成）
端侧生成完成: TTFT=640ms, decode=18.3 字/秒, 参考资料 3 段
```

然后**打开飞行模式再问一次** —— 还能答出来，就证明这条链路真的离线。

### 9.4 没有向量模型也能用

这是刻意的设计：字面检索是纯 Kotlin 实现，**不依赖任何模型**。

- 没下向量模型 → 状态显示"仅字面（未下载向量模型）"，功能可用；
- 模型加载失败 → 自动降级到仅字面，不崩不报错。

> 端侧产品的正确姿态：**缺什么就降级什么，并且告诉用户降级了什么**。
> 而不是"少个组件整个功能不可用"。

## 10. 已知局限（诚实清单）

| 局限 | 原因 | 影响 | 后续方向 |
|---|---|---|---|
| 中文语义召回弱 | 官方无多语言模型 | 主要靠字面匹配 | 换自转的多语言 TFLite；或 W8 接 MNN 的 embedder |
| 只支持 arm64 | aar 只有 arm64 so | 32 位机/模拟器不可用 | 无解（除非自己编 so） |
| 换 embedding 模型必须重建索引 | 向量空间不兼容 | 用户会疑惑"为什么搜不准" | UI 上做"重建索引"按钮 |
| 无增量更新 | 每次导入全量落盘 | 大库会慢 | 改成分片文件 + 追加写 |
| 不上 Rerank | 端侧放不下交叉编码器 | Top3 精度不如 W6 的两阶段 | 用 LLM 自己做 Rerank（慢但可行） |

**最重要的一条**：换了 embedding 模型（维度或训练语料变了），
旧索引的向量**必须全部重算**。这不是"优化"，是正确性问题 ——
两个不同模型输出的向量，就像两套不同的坐标系，摆在一起没有任何意义。

## 11. 三句话总结（面试版）

1. **RAG 不等于"本地检索"。** 按检索位置分 L0/L1/L2 三种拓扑，
   我们做的是 L2，价值是**隐私 + 离线**，代价是效果不如云端。
2. **端侧检索不能只做向量。** 官方只有英文 embedder，中文必须靠
   bigram 字面召回兜底；两路融合用 RRF，因为分数不可比、排名可比。
3. **端侧是增强项不是依赖项。** 向量模型没下、加载失败、ABI 不支持，
   统统降级到"仅字面"继续可用 —— 这条设计原则决定了所有错误处理的方向。

## 13. 真实排障实录（2026-10-26）：为什么"下不了模型、导了笔记答不上"

这三个 bug 是真机上实际踩到的，每个都值得记住 —— 不是因为难，
而是因为**现象和原因离得远**，全靠分层排查。

### Bug 1：向量模型怎么下都"失败"

**现象**：模型市场里点下载 USE 向量模型，进度走完，最后提示
"下载内容异常（仅 6120274 字节）"。

**根因**：`ModelRepository` 里有**两处**体积校验写死了 `10MB`：
`downloadFrom()` 末尾一处、`finish()` 一处。W7.5 加向量模型时
只给 `isValid()`（安装判断）加了按模型声明的 `minValidBytes`，
**下载路径这两处漏了**。USE 只有 6.1MB → 下载 100% 成功，
却在最后一步被判成"残骸" → 所有源都"失败"。

**教训**：同一个业务规则（"这个文件算不算下完了"）出现在 N 处时，
只要改了一处忘掉其余，就会造出这种"下载成功但报下载失败"的
自相矛盾。正确做法是规则只在一处定义（现在统一走 `model.minValidBytes`）。

### Bug 2：导入了笔记，问相关问题却答不上

**现象**：笔记导进去了（UI 显示 N 块），提问相关内容，
要么走云端乱答，要么说不知道。

**根因 A —— 长文档稀释**：字面相似度原来用
`hit / sqrt(|query| × |chunk|)`。块约 320 字（300 个 bigram），
提问 10 字（8 个 bigram），命中 3 个 → `3/√(8×299) ≈ 0.06`，
低于阈值 0.08 → **检索一个都不返回** → 路由回退云端 → 云端没笔记。
改成**查询包含度** `hit / |query|`（3/8 = 0.375，稳过线），
阈值语义变了，同步调到 0.15。

**根因 B —— 检索被门闩挡住**：`streamChat` 里检索套在
`if (engineReady)` 里。端侧引擎加载那几秒 / 加载失败 / 没下对话模型时，
检索根本不执行。改成**检索无条件执行**，端侧不在就"带着资料走云端"
（本地查资料 + 云端写答案，依然是合法 RAG）。

**根因 C —— 降级丢资料**：端侧推理失败回退云端时，原来只传原始问题，
检索到的资料被丢掉。现在回退也走 `withKnowledgeContext()`。

### Bug 3（环境限制，非 bug）：USE 的下载源在国内可能连不上

USE 托管在 `storage.googleapis.com`，国内直连大概率超时。
没有可信的国内镜像（HF 上搜到的都是 keras/onnx 格式，MediaPipe 用不了）。
应对：下载不了**不影响使用** —— 字面检索永远可用；
需要向量召回时挂一次代理下载即可（6MB，几秒）。

### 操作流程（修复后的完整用法，5 步）

1. **下载向量模型**：设置 → 模型市场 → 最下方"USE 文本向量模型" → 下载
   （源在 Google，国内需代理；失败也不影响第 2 步之后的流程）
2. **启用语义检索**：下载完成提示后，点"启用语义检索"
   （知识库状态会从"仅字面"变成"向量 + 字面双路"）
3. **导入笔记**：知识库卡片区 → ＋导入笔记 →
   标题填「学习计划」，正文粘贴你的真实笔记（至少 20 字）→ 导入
   （提示"已导入「学习计划」，切成 N 块"）
4. **回聊天提问**：直接问笔记里的内容，例如
   「我周三晚上安排了什么？」
5. **验证路由**：消息上方的路由徽标应显示
   "命中本地知识库 N 段，走端侧生成"；
   开飞行模式再问一次，依然能答 —— 这就是 L2 全端侧 RAG 的验收标准。

> 注意：修复 Bug 2 之前导入的笔记可能只有字面特征（当时向量模型装不上）。
> 下载好向量模型后**建议删掉重新导入一次**，让每个块都带上向量。
